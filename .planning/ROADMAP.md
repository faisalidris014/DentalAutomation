# Roadmap: DentalFlow

## Overview

DentalFlow ships in two milestones. **v1.0 Demo** (Phases 1–4, already on `main`) wires a working prototype against real APIs with a deterministic mock 835 generator — this is what runs the Ilyas presentation. **v1.1 Pilot** (Phases 3.5 → 7) replaces the mock EOB source with a real clearinghouse, reconciles PRD vs DOC scope drift, hardens HIPAA controls, and stands up the Vercel + Neon production environment for Muath's Minnesota clinic on real on-prem OpenDental.

## Milestones

- ✅ **v1.0 Demo** — Phases 1–4 (shipped before 2026-04-26)
- 🚧 **v1.1 Pilot** — Phases 3.5, 5, 6, 7 (active)

## Phases

**Phase Numbering:**
- Integer phases (1, 2, 3, 4, 5, 6, 7): Planned milestone work.
- Decimal phases (3.5): Targeted insertion to extend an existing phase. Phase 3.5 extends Phase 3 (EOB engine) to swap the mock 835 generator for a real clearinghouse — this is a hard pilot prerequisite, not optional polish.

Decimal phases appear between their surrounding integers in numeric order.

- [x] **Phase 1: Foundation, Auth & RBAC** — JWT auth, three-role RBAC, multi-tenant clinic boundary, job queue, audit log, notifications, settings, clinic/user CRUD.

## Phase Details

### Phase 1: Foundation, Auth & RBAC

**Goal**: Authenticated, role-scoped, multi-tenant API surface with audit logging, durable job queue, and notification plumbing — every later phase rides on this foundation.
**Depends on**: Nothing (first phase)
**Requirements**: REQ-AUTH-001, REQ-AUTH-002, REQ-JOBS-001, REQ-JOBS-002, REQ-AUDIT-001, REQ-NOTIF-001, REQ-CLINIC-001, REQ-USER-001, REQ-SETTINGS-001
**Success Criteria** (what must be TRUE):
  1. A user can log in with email/password and receive an access token + rotating refresh token; reusing a rotated refresh token is rejected.
  2. An `it_admin` can manage clinics and payer configs across tenants; a `staff_admin` cannot escape their `clinicId` even by passing one in a query string.
  3. Every authenticated API call is recorded to `audit_log` with no PHI in `details`.
  4. A `webhook_process` job (or any other queued job) can be enqueued, picked up by `POST /api/internal/worker`, and complete with a structured execution log that survives retries.
  5. A `staff_admin` can list, mark-read, and deep-link from notifications generated by the platform.
**Plans**: Complete (Phases 1 plans archived in commit history; no new plans needed)
**Status**: Complete (commit `1d41aaa`)

### Phase 2: PMS Sync & Eligibility Engine

**Goal**: Eligibility verification works end-to-end against real OpenDental + DentalXChange data via clean adapter boundaries, on all four trigger types (batch, day-of-service, on-demand, webhook).
**Depends on**: Phase 1
**Requirements**: REQ-PMS-001, REQ-PMS-003, REQ-SYNC-001, REQ-ELIG-001, REQ-ELIG-002, REQ-ELIG-003, REQ-ELIG-004, REQ-ELIG-005, REQ-WEBHOOK-001, REQ-PATIENT-001
**Success Criteria** (what must be TRUE):
  1. A staff user can search and view patients pulled from OpenDental into `patients_cache`, with primary insurance and recent claims attached.
  2. A staff user can click "Verify Eligibility" on a patient/insurance pair and within seconds see annual max, deductible, coverage %, copays, and waiting periods returned from the clearinghouse for a commercial payer.
  3. The nightly `eligibility_batch` job re-verifies any insurance row older than `verification_threshold_days` (default 30) and produces a single `eligibility_batch_summary` notification.
  4. An OpenDental webhook posted to `/api/webhooks/opendental` with a valid `x-webhook-secret` returns 200 immediately and triggers downstream eligibility re-verification via a queued job.
  5. The day-of-service recheck flips a previously-active insurance to `inactive` and raises an urgent `eligibility_inactive` notification before clinic open.
**Plans**: Complete
**Status**: Complete (commits `1d41aaa`, `7dbd8c1`)
**UI hint**: yes

### Phase 3: EOB Engine & Triage

**Goal**: EOBs flow from payer through parsing, triage, auto-post (or flagging), and posting back to OpenDental — on the mock 835 generator suitable for the demo and dev runs.
**Depends on**: Phase 2 (eligibility + claims sync feeds the triage engine)
**Requirements**: REQ-EOB-001, REQ-EOB-002, REQ-EOB-003, REQ-EOB-004
**Success Criteria** (what must be TRUE):
  1. A staff_admin can trigger `POST /api/eob/sync` and see `eob_records` rows materialize via the queued `eob_sync` job.
  2. EOB line items that pass all 6 triage rules auto-post to OpenDental (or to the mock writer when keys are placeholders) and surface as `auto_posted` in the EOB list.
  3. EOB line items that fail any rule flag with a deduplicated `triage_reason` and raise an `eob_flagged` notification to `staff_admin` + `it_admin`.
  4. A staff_admin can review a flagged EOB, change its status via `PUT /api/eob/:id/review`, and post the approved EOB to OpenDental via `POST /api/eob/:id/post`.
  5. The weekly `eob_report` produces counts by triage status and total dollars posted, surfaced on the dashboard.
**Plans**: Complete
**Status**: Complete (commit `083b892`)
**UI hint**: yes

### Phase 4: Frontend Wiring & Prototype UI

**Goal**: Every screen of the prototype renders against real backend data on the dark glassmorphic design system, with role-gated visibility driven by JWT role (no UI dropdown).
**Depends on**: Phase 3
**Requirements**: REQ-DASHBOARD-001, REQ-UI-001
**Success Criteria** (what must be TRUE):
  1. After login, the dashboard renders the IT-Admin / Staff-Admin / Staff-User layout matching the JWT role — there is no client-side role switcher.
  2. All 10 application screens (`/dashboard`, `/patients`, `/patients/:id`, `/eligibility`, `/recalls`, `/claims`, `/eob`, `/automations`, `/automations/:id`, `/agents`, `/notifications`, `/settings`) render against `lib/api.ts` with zero `mockApi.ts` references in the bundle.
  3. The styled-jsx design system holds: cyan #22d3ee accent on navy #0b0f1a/#1a2235/#243049, DM Sans + Space Mono, glassmorphic cards with backdrop blur and staggered animations.
  4. A 401 from the API transparently triggers a refresh+retry; a refresh failure dispatches `auth:logout` and lands the user on `/login`.
  5. The Ilyas demo can be driven through `SHOWCASE-SCRIPT.md` end-to-end without falling back to mock data.
**Plans**: Complete
**Status**: Complete (commits `7dbd8c1`, `7db2a11`, `713efa9`)
**UI hint**: yes

### Phase 3.5: Real Clearinghouse EOB Ingestion

**Goal**: Replace the deterministic mock 835 generator with a real clearinghouse integration so production EOB pulls are real payer payloads, while preserving the mock for dev/local runs.
**Depends on**: Phase 3
**Requirements**: REQ-EOB-005
**Success Criteria** (what must be TRUE):
  1. `DentalXChangeAdapter.retrieveEOBs(...)` makes real authenticated calls against the DentalXChange API for a configured pilot clinic, with credentials encrypted via the existing `payer_configs` flow.
  2. A real 835 EDI document returned by the clearinghouse is parsed into the existing `RawEOBDocument` / `RawEOBLineItem[]` shape, so downstream parser/triage/posting/notification layers run unchanged on real data.

  4. An end-to-end smoke test on Muath's pilot data pulls a real EOB → parses it → triages → either auto-posts or flags → raises the appropriate notification.
  5. A grep across the production code path returns zero references to the deterministic mock generator (mock lives only behind the dev/local flag).

### Phase 6: HIPAA Hardening

**Goal**: Operational HIPAA controls match PRD §8 in production, not just on paper — audit retention enforced, PHI scrubbing verified, key rotation runbook in place, BAAs signed.
**Depends on**: Phase 5 (resolved scope clarifies what's regulated)
**Requirements**: REQ-HIPAA-001
**Success Criteria** (what must be TRUE):
  1. `audit_log` is retained for 6 years via a documented archive policy (Neon-native partitioning + S3/Blob with object-lock OR equivalent) with the retention enforcement script tested against synthetic PHI; `docs/deployment.md` reflects 6 years instead of 90 days.
  2. A PHI-scrubbing audit confirms the `errorHandler` middleware redacts SSN patterns, phone, email, DOB, and insurance IDs from any error before log emit, with regression tests guarding the redaction list.
  3. A documented key rotation runbook exists for `JWT_SECRET`, `CREDENTIAL_ENCRYPTION_KEY`, and `WEBHOOK_SECRET`, including how to rotate without breaking active sessions or webhook senders.
  4. Vercel BAA and Neon BAA are signed, dated, and referenced from `docs/deployment.md`.
  5. A pre-deploy HIPAA checklist is added to the deployment guide and runs green for the pilot environment.

### Phase 7: Pilot Production Deployment

**Goal**: Muath's Minnesota clinic running on real on-prem OpenDental against the production Vercel + Neon environment with real DentalXChange EOB ingestion, auto-posting working end-to-end.
**Depends on**: Phase 6
**Requirements**: REQ-PMS-002, REQ-PILOT-001
**Success Criteria** (what must be TRUE):
  1. A production Vercel deployment serves `${APP_URL}` against a Neon production database, with all environment variables (including a 32-byte `CREDENTIAL_ENCRYPTION_KEY` unique to prod and a real `WEBHOOK_SECRET`) provisioned via Vercel project env management.
  2. `POST /api/internal/worker` is invoked by Vercel Cron and authenticates via Vercel-injected `CRON_SECRET` instead of `Bearer ${JWT_SECRET}`; the migration is verified by a green cron run on the production schedule.
  3. Muath's pilot clinic is provisioned in `clinics` with real OpenDental dual keys (developer + customer), real `pms_config` (api_mode + base_url), and real `payer_configs` rows for Delta Dental, MetLife, and Cigna routed to DentalXChange — no `placeholder` keys remain in production.
  4. On-premise OpenDental connectivity is established via either a lightweight Node.js local agent on the clinic LAN with an outbound WebSocket OR a documented VPN tunnel, with `pmsAdapter.testConnection()` returning green from production against the clinic.
  5. A real EOB pulled from DentalXChange against Muath's clinic on production data parses → triages → auto-posts or flags → posts back to OpenDental → raises notifications, all observable in the production audit log and dashboard.
