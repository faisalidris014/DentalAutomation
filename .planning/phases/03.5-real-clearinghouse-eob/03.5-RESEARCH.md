# Phase 3.5: Real Clearinghouse EOB Ingestion — Research

**Researched:** 2026-04-26
**Domain:** Healthcare EDI 835 ingestion, dental clearinghouse APIs, serverless ingestion on Vercel + Neon
**Confidence:** MEDIUM (HIGH on parser/pattern decisions; LOW on DentalXChange-specific API surface — see Open Questions)

## Summary

Phase 3.5 swaps the deterministic mock 835 generator inside `DentalXChangeAdapter.retrieveEOBs()` for a real production EOB source while keeping the mock available for dev/local. The hard architectural decision is **which "real" source to wire up**: DentalXChange's XConnect Payment API (preferred — Muath is already a DXC + Open Dental shop) or a parallel route via Stedi (an API-first clearinghouse that returns 835s as JSON).

DentalXChange has a developer portal at `developer.dentalxchange.com` with a "Payment API" tile, but **all detailed endpoint documentation is gated behind login/registration**. Three independent fetches (developer portal home, Payment API page, Postman workspace) returned only navigation chrome — no endpoint specs, no auth scheme, no sandbox URL. We cannot author a production-quality plan against the DXC API without first obtaining partner credentials and the actual API spec. This is a real blocker, not a gap we can paper over.

Two viable plan shapes follow from that:

1. **Plan A (DentalXChange-direct, contingent on credentials):** Contact DXC partner enrollment, get sandbox + Payment API spec, implement an HTTP client that pulls 835 EDI files and parses them with `x12-parser` (the only TypeScript-native, actively-maintained X12 library on npm — last release 2024-09-21, v1.3.0).
2. **Plan B (Stedi-via-abstraction):** Wire to Stedi's GA dental clearinghouse, which returns 835 ERAs as JSON — bypasses the EDI parsing problem entirely. The interface stays identical (`retrieveEOBs` returns `RawEOBDocument[]`); only the source changes.

**Primary recommendation:** Build the phase around an abstracted `RealClearinghouseEOBSource` interface, ship Plan A (DXC) as the production target since Muath's clinic is already on DXC + Open Dental, and keep Stedi documented as a pre-validated fallback. Drive the mock-vs-real switch off `payer_configs.featuresEnabled.eobMode` (`'mock' | 'sandbox' | 'production'`) — same shape as the existing OpenDental `PMS_MOCK_MODE` precedent (D-015), but per-payer-config not per-clinic.

### Pattern 1: Adapter Delegates to a Source Object

**What:** `DentalXChangeAdapter.retrieveEOBs` becomes a 3-line dispatch that picks a source object based on `eobMode`. Both source objects implement the same internal interface.

**When to use:** When you have multiple back-ends for the same operation (mock vs real, prod vs sandbox) AND want them to be unit-testable in isolation.

**Example:**
```typescript
// Source: this codebase's existing pattern in server/adapters/pms/opendental/adapter.ts
// (isMockMode flag at constructor + branching at write methods)

interface IClearinghouseEOBSource {
  fetch(params: { dateFrom: string; dateTo: string; clinicNpi: string }):
    Promise<RawEOBDocument[]>;
}

class DentalXChangeAdapter implements IPayerAdapter {
  private eobSource: IClearinghouseEOBSource;

  constructor(payerName: string, config?: { eobMode?: 'mock' | 'sandbox' | 'production'; credentials?: DXCCredentials }) {
    this.payerName = payerName;
    const mode = config?.eobMode ?? this.inferDefaultMode(config);
    this.eobSource = mode === 'mock'
      ? new MockEOBSource(payerName)
      : new RealClearinghouseEOBSource({ payerName, env: mode, credentials: config!.credentials! });
  }

  private inferDefaultMode(config?: { credentials?: DXCCredentials }): 'mock' | 'production' {
    if (process.env.PAYER_MOCK_MODE === 'true') return 'mock';
    if (!config?.credentials || config.credentials.apiKey === 'placeholder') return 'mock';
    return 'production';
  }

  async retrieveEOBs(params: { dateFrom: string; dateTo: string; clinicNpi: string }) {
    return this.eobSource.fetch(params);
  }
}
```

### Pattern 2: Stream-Based 835 Parsing

**What:** Use `x12-parser`'s Transform stream to consume the 835 segment-by-segment, accumulating into a tree keyed by claim (CLP) → service line (SVC).

**When to use:** Always for 835 — even small files. Stream API gives you a clean event loop without buffering megabytes of EDI text.

**Example pseudocode (verify against `x12-parser` docs before final):**
```typescript
// Source: tastypackets/x12-parser README (as of v1.3.0, 2024-09-21)
import { X12Parser, X12grouper } from 'x12-parser';
import { Readable } from 'stream';

async function parse835(rawEdi: string): Promise<Parsed835> {
  const claims: ParsedClaim[] = [];
  let currentClaim: ParsedClaim | null = null;
  let payer: PayerInfo | null = null;
  let payee: PayeeInfo | null = null;
  let payment: PaymentInfo | null = null;

  const stream = Readable.from([rawEdi]).pipe(new X12Parser());

  for await (const seg of stream) {
    switch (seg.name) {
      case 'BPR':
        // BPR02 = check amount, BPR04 = method, BPR05 = check number, BPR06 = check date
        payment = { amount: Number(seg.elements[1]), checkNumber: seg.elements[4], checkDate: seg.elements[5] };
        break;
      case 'TRN':
        // TRN02 = trace number — match to bank EFT
        if (payment) payment.traceNumber = seg.elements[1];
        break;
      case 'N1':
        if (seg.elements[0] === 'PR') payer = { name: seg.elements[1] };
        if (seg.elements[0] === 'PE') payee = { name: seg.elements[1], npi: seg.elements[3] };
        break;
      case 'CLP':
        // CLP01 = claim ID, CLP03 = total charge, CLP04 = paid, CLP05 = patient resp
        if (currentClaim) claims.push(currentClaim);
        currentClaim = {
          claimPmsId: seg.elements[0],
          billed: Number(seg.elements[2]),
          paid: Number(seg.elements[3]),
          patientResp: Number(seg.elements[4]),
          serviceLines: [],
        };
        break;
      case 'NM1':
        if (currentClaim && seg.elements[0] === 'QC') {
          currentClaim.patientFirstName = seg.elements[3];
          currentClaim.patientLastName = seg.elements[2];
        }
        break;
      case 'SVC':
        // SVC01 = procedure code (CDT for dental), SVC02 = billed, SVC03 = paid, SVC04 = revenue code (n/a dental)
        if (currentClaim) {
          currentClaim.serviceLines.push({
            procedureCode: parseCompositeCode(seg.elements[0]).code,
            fee: Number(seg.elements[1]),
            paid: Number(seg.elements[2]),
            // allowed/adjustment computed from CAS segments below
          });
        }
        break;
      case 'CAS':
        // Adjustment reasons: CAS01 = group code (CO/PR/OA/PI), CAS02 = reason code (CARC)
        // Apply to currentLine if inside SVC, else to currentClaim
        applyCasAdjustment(currentClaim, seg);
        break;
      case 'DTM':
        // DTM01 = qualifier (472 = service date), DTM02 = date
        if (currentClaim && seg.elements[0] === '472') {
          currentClaim.serviceLines[currentClaim.serviceLines.length - 1].serviceDate = seg.elements[1];
        }
        break;
      case 'PLB':
        // Provider-level adjustments — track separately, apply at check level not claim level
        break;
    }
  }
  if (currentClaim) claims.push(currentClaim);
  return { payer, payee, payment, claims };
}
```
Note: this is a sketch demonstrating the segment-handling pattern. Verify `x12-parser` API surface (event names, segment property naming) against its README before locking the implementation. `[CITED: github.com/tastypackets/x12-parser]`

### Anti-Patterns to Avoid

- **Hardcoding EDI delimiters.** The 835 ISA segment defines element separator (`*`), repetition separator (ISA11), component separator (ISA16), and segment terminator. Senders vary. Always read from ISA. Source: edifileconverter.com/articles/troubleshoot-edi-835-837-parsing-errors. `x12-parser` already does this correctly per its README.
- **Treating one ERA-per-payment as universal.** A single 835 can carry many CLP segments (multiple patients, sometimes multiple checks via PLB takeback). The existing dedupe key `(clinicId, checkNumber, payerName)` is fine — but be aware: a real check covers many patients, unlike the mock which generates one EOB per `RawEOBDocument`.
- **Trusting the BPR check amount as the sum of CLP04 paid amounts.** PLB segments adjust check totals (interest, prior overpayment recovery, withholds). The reconciliation rule: `BPR02 = sum(CLP04) + net(PLB)`. If reconciliation fails, flag the EOB rather than blindly posting. `[CITED: accountablehq.com/post/hipaa-835-file-format-a-developer-s-guide-to-edi-era-segments-loops-and-validation]`
- **Logging raw 835 text.** Real 835s contain SSN/DOB/insurance ID — full PHI. Existing `errorHandler` PHI scrub list MUST be audited against real 835 patterns before production. Phase 6 explicitly schedules this; Phase 3.5 must surface the gap.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| 835 EDI parsing | Hand-rolled segment splitter | `x12-parser` v1.3.0 | 835 has 7 SNIP validation levels, variable delimiters from ISA, nested loops (1000A/B, 2000, 2100, 2110), and dental-specific tooth/oral-cavity REF qualifiers. Hand-rolling = ~800 LOC + ongoing maintenance burden. `[CITED: accountablehq.com — HIPAA 835 developer guide]` |
| Credential encryption | New AES wrapper | `server/services/encryption/credentials.ts` | Already AES-256-GCM via `encrypt()` / `decrypt()`. Same key (`CREDENTIAL_ENCRYPTION_KEY`) used for OpenDental + payer credentials. Adding a parallel encryption path violates D-006. |
| Job retry logic | Custom retry loop in adapter | Existing `eob_sync` job + worker retry | Worker already retries with exponential backoff `1000 * 60 * 2^retryCount`, max 3 retries. `[VERIFIED: server/services/queue/worker.ts:215–225]`. | EOB deduplication | Hash-based dedup in adapter | Existing `(clinicId, checkNumber, payerName)` uniqueness check | `[VERIFIED: server/services/eob/engine.ts:71–84]`. ## Common Pitfalls

### Pitfall 1: ERA mode field placement collides with existing `featuresEnabled.eob` boolean

**What goes wrong:** `payer_configs.featuresEnabled` is a JSONB column. Phase 3 uses `featuresEnabled.eob === false` to skip EOB sync entirely (`[VERIFIED: server/services/eob/engine.ts:54]`). If Phase 3.5 adds `featuresEnabled.eobMode = 'mock' | 'production'`, the existing boolean check still works — but a row with `{ eob: false, eobMode: 'production' }` will still be skipped.

**Why it happens:** Two flags with overlapping semantics in the same JSONB.

**How to avoid:** Document precedence explicitly: `eob: false` ALWAYS skips, regardless of `eobMode`. `eob: true` (or absent — default) plus `eobMode === 'mock'` → run with mock. `eob: true` plus `eobMode === 'production'` → run with real. Add a unit test asserting this precedence.

**Warning signs:** A clinic disables EOB feature but real ERAs keep posting (means `eob: false` was ignored). Or: tests pass with `{ eob: true }` but production hangs because credentials are missing and the code didn't fall back to mock.

### Pitfall 2: Vercel function timeout on the first ERA backlog

**What goes wrong:** A new pilot clinic enrolling fresh has 30+ days of unpulled ERAs from each enrolled payer. The first `eob_sync` may need to download and parse dozens of 835 files in one invocation, blowing past the 300s default.

**Why it happens:** `syncEobs(clinicId)` loops over ALL enabled payer configs and processes ALL returned ERAs serially in one call. Default Fluid Compute timeout is 300s (5min) on all plans; max is 800s on Pro. `[CITED: vercel.com/changelog/higher-defaults-and-limits-for-vercel-functions-running-fluid-compute]`

**How to avoid:** Two options, choose one:
- **(A) Bound the date window per call.** Default `dateFrom = today - 30 days` (existing). Add a new env var or config: `EOB_SYNC_MAX_DAYS_PER_CALL = 7`. The job loops day-by-week and enqueues a follow-up `eob_sync` if the window isn't fully drained.
- **(B) One job per (clinicId, payerConfigId, dateRange).** Decompose the loop in `syncEobs`: instead of processing all configs in one job, the parent job enqueues child `eob_sync` jobs (one per payer config). Each child handles one payer for one date range — bounded work, parallelizable.

Recommend **(B)** because it parallelizes across Vercel function invocations (Fluid Compute reuses instances, but each job invocation is still bounded). Set `maxDuration = 300` explicitly in `app/api/internal/worker/route.ts` route segment config to be explicit. `[CITED: vercel.com/docs/functions/configuring-functions/duration]`

**Warning signs:** First sync after enrollment fails with 504 FUNCTION_INVOCATION_TIMEOUT. Job log shows status=running with no completion entry.

### Pitfall 3: ISA delimiter assumption breaks on a non-default-delimiter payer

**What goes wrong:** Some senders use `|` instead of `*` as element separator, or `\n` vs `~` as segment terminator. If the parser hardcodes them, parsing produces garbage or single-segment output.

**Why it happens:** Tutorial code commonly hardcodes `*` and `~`.

**How to avoid:** Use `x12-parser`, which reads delimiters from the ISA segment automatically. Test with at least one fixture that uses non-default delimiters. `[CITED: edifileconverter.com/articles/troubleshoot-edi-835-837-parsing-errors]`

**Warning signs:** All segments in the parsed output are `null` or all data appears in a single field. Most parsers at least preserve the ISA segment, so check whether you get >1 segment from the parser before trusting any result.

### Pitfall 4: PHI in error messages from the new parser

**What goes wrong:** When 835 parsing fails (malformed EDI, missing required segment), the parser may throw an error that includes a snippet of the raw EDI — and that snippet may contain a real SSN, DOB, or insurance ID.

**Why it happens:** Generic parser libraries don't know about HIPAA. The current `errorHandler` middleware scrubs SSN / phone / email / DOB / insurance IDs from `err.message` before logging — but only for known patterns. An EDI snippet like `NM1*QC*1*DOE*JANE****MI*123456789~` passes the SSN pattern but fails any structured field detection.

**How to avoid:** Wrap all `x12-parser` calls in a try/catch in the adapter. On failure, throw a sanitized error: `new PayerConnectionError('835 parse failed: <segment name> at offset <N>')` — never include raw EDI in the thrown message. Add an explicit unit test: feed malformed EDI, assert the thrown error contains no digit-runs of length >=8.

**Warning signs:** Error logs containing strings that look like NM1, REF, NM1*QC, or any 9+ digit number. Phase 6 PHI-scrubbing audit must extend its regex set to cover EDI segment patterns.

### Pitfall 5: Dental tooth-number / oral-cavity data is in a different place than CDT code

**What goes wrong:** The mapper extracts CDT procedure code from SVC01 but assumes `toothNumber` is also in SVC. In the 5010 spec, dental tooth numbers live in REF/SV3 segments under loop 2110, and a fact-sheet from WEDI (2026-03-06) flagged that 8020 introduces a dedicated tooth segment — so the location is a moving target. `[CITED: wedi.org/2026/03/06/fact-sheet-whats-new-in-version-8020-x12-implementation-guides-tooth-segment-information-in-the-835-transaction-set]`

**Why it happens:** Most generic 835 parser examples are medical (CPT codes, no tooth concept).

**How to avoid:** Read Delta Dental's 835 companion guide (PDF: deltadentalins.com/content/dam/ddins/en/pdf/dentists/companion-guide-835.pdf) before writing the mapper. Add unit tests with real (anonymized) 835 fixtures from Delta Dental, MetLife, and Cigna. Make `toothNumber` field on `RawEOBLineItem` optional (already is) and accept that some payers won't populate it.

**Warning signs:** All `toothNumber` fields come back undefined in production but were populated in mock data. Triage rule that depends on tooth (none today, but future) misbehaves.

### Pitfall 6: DXC issues distinct credentials per API surface

**What goes wrong:** DXC may issue separate credentials for Eligibility API vs Payment API. Existing `payer_configs.credentials` stores a single encrypted blob assumed to contain one credential set. If two are needed, the blob shape changes.

**Why it happens:** Without published API docs, we can't confirm whether one OAuth client / API key covers all XConnect APIs or whether each (Eligibility, Claim, Payment, Account) has separate credentials.

**How to avoid:** Design `decryptDXCCredentials()` to accept either shape: `string` (legacy, single credential) OR `JSON({ eligibility?: {...}, payment?: {...} })`. Store new credentials in the JSON shape; keep the string form working for backward compatibility with the eligibility code path.

**Warning signs:** EOB sync fails with 401 against DXC even though eligibility verification still works for the same payer config.

### Mock-vs-real dispatch (matches existing OpenDental precedent)

```typescript
// File: server/adapters/payer/clearinghouse/dentalxchange.ts (refactored)
// Precedent: server/adapters/pms/opendental/adapter.ts:34–42

import type { IPayerAdapter, RawEOBDocument } from '../types';
import { MockEOBSource } from './dentalxchange-source-mock';
import { RealClearinghouseEOBSource } from './dentalxchange-source-real';
import type { IClearinghouseEOBSource } from './source-types';
import { decrypt } from '../../../services/encryption/credentials';

export interface DXCCredentialsBlob {
  eligibility?: { apiKey: string };
  payment?: { apiKey: string; baseUrl?: string };
  // Legacy shape: a bare string is decrypted into apiKey for both surfaces.
}

export class DentalXChangeAdapter implements IPayerAdapter {
  readonly payerName: string;
  readonly payerType = 'commercial' as const;
  private eobSource: IClearinghouseEOBSource;

  constructor(payerName: string, opts?: { eobMode?: 'mock' | 'sandbox' | 'production'; encryptedCredentials?: string | null }) {
    this.payerName = payerName;
    const mode = this.resolveMode(opts);
    this.eobSource = mode === 'mock'
      ? new MockEOBSource(payerName)
      : new RealClearinghouseEOBSource({ payerName, env: mode, credentials: this.parseCredentials(opts?.encryptedCredentials) });
  }

  private resolveMode(opts?: { eobMode?: 'mock' | 'sandbox' | 'production'; encryptedCredentials?: string | null }): 'mock' | 'sandbox' | 'production' {
    // Precedence: explicit eobMode → env override → presence of credentials → mock by default.
    if (opts?.eobMode) return opts.eobMode;
    if (process.env.PAYER_MOCK_MODE === 'true') return 'mock';
    if (!opts?.encryptedCredentials) return 'mock';
    return 'production';
  }

  private parseCredentials(encrypted: string | null | undefined): DXCCredentialsBlob {
    if (!encrypted) return {};
    const decrypted = decrypt(encrypted);
    try { return JSON.parse(decrypted) as DXCCredentialsBlob; }
    catch { return { eligibility: { apiKey: decrypted } }; } // Legacy single-string form
  }

  async retrieveEOBs(params: { dateFrom: string; dateTo: string; clinicNpi: string }): Promise<RawEOBDocument[]> {
    return this.eobSource.fetch(params);
  }

  // checkEligibility, testConnection, getHealthStatus — preserve existing implementations
  // (eligibility code path is out of scope for Phase 3.5).
}
```

   - What we know: ClaimConnect (DXC's web UI) lets users download `.835` EDI files. APIs in this space generally serve raw EDI; Stedi is an outlier.
   - What's unclear: Whether the Payment API serves the raw EDI bytes or a JSON projection.

   - What we know: DXC's developer portal has a register/login flow. Partners typically issue API keys for B2B integrations.
