## 1. Architecture Overview

### Core Principle: PMS-Agnostic Design

DentalFlow's business logic NEVER talks directly to OpenDental (or any PMS). Every interaction goes through an adapter layer. This means adding support for EagleSoft, SoftDent, Dentrix, or Curve Dental later is just creating a new adapter file — zero changes to business logic.

The same principle applies to insurance payers. Every payer (Delta Dental, Health Partners, DentaQuest, etc.) gets its own adapter. The eligibility engine calls the adapter interface; the adapter handles the specifics.

## 2. Database Schema

Use **Drizzle ORM** with **PostgreSQL**. All tables use UUID primary keys. All timestamps are UTC. All PHI fields are encrypted at rest by PostgreSQL's built-in encryption or application-level AES-256 where noted.

### clinics

The central entity. Every patient, user, job, and configuration belongs to a clinic.

```typescript
clinics = pgTable('clinics', {
  id:                uuid('id').primaryKey().defaultRandom(),
  name:              text('name').notNull(),
  address:           text('address'),
  city:              text('city'),
  state:             text('state'),                          // 2-letter state code
  zip:               text('zip'),
  phone:             text('phone'),
  npi:               text('npi'),                            // National Provider Identifier
  pms_type:          text('pms_type').notNull(),              // 'opendental' | 'eaglesoft' | 'softdent' | etc.
  pms_config:        jsonb('pms_config').notNull(),           // PMS-specific connection config (see below)
  status:            text('status').notNull().default('active'), // active | inactive | setup
  timezone:          text('timezone').default('America/Chicago'),
  created_at:        timestamp('created_at').defaultNow(),
  updated_at:        timestamp('updated_at').defaultNow(),
});

// pms_config shape for OpenDental:
// {
//   api_mode: 'remote' | 'local' | 'service',
//   base_url: 'https://api.opendental.com/api/v1',    // or local URL
//   developer_key: 'encrypted_string',                  // NiftyByte's dev key
//   customer_key: 'encrypted_string',                   // clinic-specific key
//   econnector_url: string | null,                      // for remote mode
//   api_tier: 'free' | 'basic' | 'standard' | 'full',
//   last_sync_at: ISO timestamp,
//   sync_interval_minutes: 60,
// }
//
// pms_config shape for EagleSoft (future):
// {
//   api_mode: 'pic',
//   base_url: string,
//   client_id: 'encrypted_string',
//   client_secret: 'encrypted_string',
//   ...
// }
```

### patients_cache

Local cache of patient data synced from the PMS. This is NOT the source of truth — the PMS is. This cache enables fast lookups and reduces API calls.

```typescript

  id:                uuid('id').primaryKey().defaultRandom(),
  clinic_id:         uuid('clinic_id').references(() => clinics.id).notNull(),
  pms_patient_id:    text('pms_patient_id').notNull(),       // OpenDental: PatNum. EagleSoft: their ID.
  first_name:        text('first_name').notNull(),
  last_name:         text('last_name').notNull(),
  date_of_birth:     date('date_of_birth'),
  gender:            text('gender'),                          // M | F | Other | Unknown
  phone_home:        text('phone_home'),
  phone_cell:        text('phone_cell'),
  email:             text('email'),
  address:           text('address'),
  city:              text('city'),
  state:             text('state'),
  zip:               text('zip'),
  guarantor_id:      text('guarantor_id'),                    // PMS guarantor reference
  preferred_contact: text('preferred_contact'),                // email | phone | text
  balance:           decimal('balance', { precision: 10, scale: 2 }).default('0'),
  status:            text('status').default('active'),         // active | inactive | archived
  last_synced_at:    timestamp('last_synced_at'),

  clinicPmsIdx: uniqueIndex('idx_patient_clinic_pms').on(table.clinic_id, table.pms_patient_id),

```

// Key implementation notes:
//
// 1. AUTH: Every request includes two headers:
//    - Authorization: ODFHIR {DeveloperKey}/{CustomerKey}
//    - Content-Type: application/json
//
// 2. CONNECTION MODE: Pilot clinic uses ON-PREMISE OpenDental
//    - Primary: Local API or API Service mode (direct to clinic server)
//    - Requires network access to clinic server (VPN or local agent)
//    - NO rate limiting in Local/Service mode
//    - Pagination: 1,000 items per request (vs 100 on Remote)
//    - Fallback: Remote mode via eConnector if direct access is not feasible
//
// 3. RATE LIMITING: Built into the client.ts HTTP wrapper
//    - Local/Service mode: NO throttling (but still be respectful of clinic server load)
//    - Remote mode (sandbox/fallback): 1 req per 5 seconds read, 1 req per 1 second write
//    - Implement adaptive throttling: detect mode from clinic config, apply appropriate limits
//
// 4. PAGINATION: OpenDental uses Offset parameter
//    - Local/Service: max 1,000 per request
//    - Remote: max 100 per request
//    - Loop until items.length < limit
//
// 5. INCREMENTAL SYNC: Use DateTStamp field
//    - Most OpenDental tables have a DateTStamp column that auto-updates
//    - GET /patients?DateTStamp=2026-04-18T00:00:00 returns only patients modified since that date
//
// 6. ERROR HANDLING: OpenDental returns HTTP 200 for most errors
//    - Check response body for error indicators
//    - Wrap in consistent error types
//
// 7. LOCAL AGENT ARCHITECTURE (for on-premise connections):
//    - A lightweight Node.js agent runs on the clinic network
//    - Agent maintains outbound WebSocket connection to DentalFlow cloud (Azure)
//    - DentalFlow cloud sends API requests through the WebSocket tunnel
//    - Agent forwards requests to the local OpenDental API and returns responses
//    - This avoids inbound firewall rules at the clinic
//    - Agent also handles webhook registration (OpenDental sends webhooks to the local agent,
//      which forwards them to DentalFlow cloud)

// Endpoint mapping for each IPMSAdapter method:
//
// getPatients()           → GET /patients?DateTStamp={modifiedSince}&Limit={limit}&Offset={offset}
// getPatientById()        → GET /patients/{PatNum}
// getAppointments()       → GET /appointments?AptDateTime={dateFrom}&AptStatus=Scheduled

## 5. Eligibility Engine

The eligibility engine is the core product. It orchestrates verification across payers and manages the full lifecycle.

### Nightly Batch Flow

```
TRIGGER: Cron job runs at configurable time (default 10 PM clinic local time)

STEP 1: Pull upcoming appointments
  - Call pmsAdapter.getAppointments({ dateFrom: today, dateTo: today + lookahead_days })
  - Default lookahead: 3 days
  - Get unique patient list from appointments

STEP 2: For each unique patient, check if verification is needed
  - Call pmsAdapter.getVerificationStatus(patPlanPmsId)
  - If lastVerifiedDate is within threshold (default 30 days for Medicaid) → SKIP
  - If lastVerifiedDate is stale or null → QUEUE for verification

STEP 3: For each patient needing verification
  - Get insurance info: pmsAdapter.getInsurancePlans(patientPmsId)
  - Classify: is this Medicaid or commercial?
    - Use classifier.ts which checks carrier name against known Medicaid carriers per state
    - Route to appropriate payer adapter via registry

STEP 4: Execute verification
  - Call payerAdapter.checkEligibility(request)
  - Handle result:
    - active → write back to PMS, log to eligibility_checks
    - inactive → write back to PMS, create notification (warning), log
    - unknown/failed → create notification (action_required), log, flag for manual review

STEP 5: Write results back to PMS
  - Call pmsAdapter.writeVerificationResult({
      patPlanPmsId,
      verifyDate: today,
      verifyNote: `DentalFlow auto-verified: ${result.status}`
    })
  - Update eligibility_checks.written_to_pms = true

STEP 6: Create job record
  - Log the entire batch as a job in the jobs table
  - Include execution_log with step-by-step trace
  - Track total_items, processed_items, failed_items

STEP 7: Generate notifications
  - If any patients are inactive → notification to staff_admin + staff_user
  - If any verifications failed → notification to staff_admin
  - If batch itself failed → notification to it_admin
```

### On-Demand Verification

Triggered from the Eligibility screen when a staff member clicks "Verify" for a specific patient.

```
INPUT: patient_id, insurance_id (from the UI)

1. Look up patient and insurance from cache
2. Get fresh insurance info from PMS (in case it changed since last sync)
3. Classify payer type
4. Execute verification via payer adapter
5. Write result back to PMS
6. Update local cache
7. Return result to UI immediately (no job queue — synchronous for on-demand)
8. Log to eligibility_checks and audit_log
```

### Day-of-Service Recheck

Lightweight recheck on the morning of appointment day.

```
TRIGGER: Cron job at 6 AM clinic local time

1. Pull today's appointments only
2. For each patient, do a quick active/inactive check (no full benefits)
3. If status changed since last verification → create urgent notification
4. Do NOT write back to PMS (lightweight, no write overhead)
5. Log to eligibility_checks with trigger = 'batch_recheck'
```

## 6. EOB Engine

EOB (Explanation of Benefits) is the second product. It handles retrieving EOB documents from payers and posting the payment information into the PMS.

### EOB Retrieval

```
TRIGGER: Configurable schedule (default: weekly on Monday at 7 AM)

1. For each enabled payer in payer_configs:
   a. Connect to payer portal or receive EDI 835 files
   b. Retrieve all new EOBs since last retrieval date
   c. Parse EOB data into structured format (line items)
   d. Store in eob_records table with triage_status = 'pending'

2. Each EOB record contains:
   - Check number, check date, check amount
   - Line items: patient, service date, procedure, amounts, denials
```

### EOB Triage (Auto-Post vs Flag)

This is the logic that handles 90-95% automatically and flags the rest for human review.

```
FOR EACH EOB line item:

AUTO-POST if ALL of these are true:
  ✓ Patient found in PMS (by name + DOB or patient ID)
  ✓ Matching claim found in PMS (by service date + procedure code)
  ✓ Paid amount > $0 (not a zero-pay)
  ✓ Paid amount ≤ configurable threshold (default $250 — above this, flag for review)
  ✓ No denial code present
  ✓ Amounts reconcile (allowed ≤ fee charged)

FLAG FOR REVIEW if ANY of these are true:
  ✗ Zero pay (paid amount = $0) — ALWAYS flagged per Ilyas's process
  ✗ Patient not found in PMS
  ✗ No matching claim found
  ✗ Paid amount exceeds threshold
  ✗ Denial code present
  ✗ Amount mismatch (allowed > fee charged, or other inconsistency)
  ✗ Duplicate EOB (same check number already posted)

TRIAGE RESULT stored in eob_records:
  - triage_status: 'auto_posted' | 'flagged_for_review'
  - triage_reason: description of why flagged (if applicable)
```

### EOB Posting to PMS

For auto-approved line items:

```
1. Create insurance payment in PMS:
   - pmsAdapter.postInsurancePayment({
       checkNumber, checkDate, checkAmount, carrierName,
       lineItems: [{ claimPmsId, procedureCode, amountPaid, ... }]
     })

2. Update eob_records:
   - posted_to_pms = true
   - pms_claim_payment_id = result.pmsRecordId
   - posted_at = now

3. Log to audit_log
```

### Weekly Summary Report

Generated after each EOB posting cycle.

```
REPORT CONTENTS:
  - Total EOBs processed this week
  - Total amount posted
  - Number of auto-posted items
  - Number of flagged items (with reasons)
  - List of flagged items needing attention:
    - Patient name, service date, amount, flag reason
  - Denied claims summary:
    - Patient name, denial reason, amount denied

DELIVERY:
  - Displayed in DentalFlow dashboard
  - Available as downloadable report
  - Optional: email to staff_admin (future)
```

## 8. Authentication & Security

### JWT Authentication

```
Token structure:
{
  sub: user.id,
  email: user.email,
  role: user.role,          // 'it_admin' | 'staff_admin' | 'staff_user'
  clinic_id: user.clinic_id, // null for it_admin
  iat: issued_at,
  exp: expires_at            // 15 minutes
}

Refresh token: UUID stored in database, 7-day expiry, single use
```

### Role-Based Access Control

```
Middleware checks on every route:

IT Admin:
  ✓ All routes
  ✓ All clinics
  ✓ /api/agents (exclusive)
  ✓ /api/clinics POST (create)

Staff Admin:
  ✓ Most routes — scoped to their clinic_id
  ✓ /api/eob (exclusive — Staff Users can't see EOB)
  ✓ /api/users POST (invite staff within their clinic)
  ✗ /api/agents
  ✗ /api/clinics POST

Staff User:
  ✓ Read routes — scoped to their clinic_id
  ✓ /api/eligibility/verify (can run verifications)
  ✓ /api/notifications (filtered — no agent/IT notifications)
  ✗ /api/eob
  ✗ /api/agents
  ✗ /api/users POST
  ✗ /api/settings (except notification preferences)
```

### HIPAA Compliance

```
REQUIRED from day one:

1. Encryption in transit: HTTPS only (TLS 1.2+)
2. Encryption at rest: PostgreSQL with encrypted storage, AES-256 for payer credentials
3. Audit logging: Every PHI access logged to audit_log table
4. Access control: JWT + RBAC — no shared accounts, no role escalation
5. PHI scrubbing: Error messages and logs NEVER contain patient names, DOBs, SSNs, or insurance IDs
6. Session management: 15-minute token expiry, refresh rotation
7. Password policy: bcrypt with salt rounds ≥ 12, minimum 8 characters
8. Data retention: Audit logs retained for 6 years (HIPAA requirement)
```

## 9. Job Queue System

All background automation runs through the job queue.

### Job Types

```
SYNC JOBS:
  sync_patients          — Pull patient data from PMS
  sync_appointments      — Pull appointment data from PMS
  sync_insurance         — Pull insurance data from PMS
  sync_claims            — Pull claims data from PMS

ELIGIBILITY JOBS:
  eligibility_batch      — Nightly batch verification (multiple patients)
  eligibility_single     — On-demand single patient verification
  eligibility_recheck    — Day-of-service recheck

EOB JOBS:
  eob_sync               — Retrieve EOBs from payer portals
  eob_post               — Post approved EOBs to PMS
  eob_report             — Generate weekly summary report

SYSTEM JOBS:
  webhook_process        — Process incoming webhook event
```

### Job Lifecycle

```
QUEUED → RUNNING → COMPLETED
                 → FAILED → RETRYING → RUNNING → ...
                 → CANCELLED

- Jobs are picked up by the worker in priority order (1 = highest)
- Failed jobs retry up to max_retries times with exponential backoff
- Running jobs that exceed timeout are marked as failed
- Execution steps are logged in real-time to execution_log JSON array
```

### Worker Implementation

```
The job worker runs as a background process (or Next.js cron route).

Loop:
  1. Query for next job: status = 'queued', ORDER BY priority ASC, created_at ASC
  2. Set status = 'running', started_at = now()
  3. Execute job based on job_type
  4. On success: status = 'completed', duration_ms = elapsed
  5. On failure: if retry_count < max_retries → status = 'retrying', schedule next retry
                 else → status = 'failed', create notification
  6. Update execution_log with each step
```

## 10. Webhook Receiver

OpenDental sends webhooks (API Events) when data changes.

### Supported Events

```
Database Events (fire when table columns change):
  - appointment.created    → Queue eligibility check for the patient
  - appointment.updated    → Re-check if insurance needs re-verification
  - patplan.created        → Queue eligibility check (new insurance added)
  - patplan.updated        → Queue re-verification (insurance changed)
  - patplan.deleted        → Update insurance_cache, mark as inactive
  - patient.updated        → Update patients_cache

UI Events (fire on user actions):
  - patient.selected       → Optionally pre-fetch insurance data
```

### Webhook Handler

```
1. Receive POST /api/webhooks/opendental
2. Verify source (IP whitelist or signature — OpenDental's approach)
3. Parse payload via pmsAdapter.parseWebhookPayload()
4. Create a job: job_type = 'webhook_process', store event data
5. Return 200 immediately (don't process inline — OpenDental has a 3-day retry queue)
6. Worker picks up the job and routes to appropriate handler
```

## 15. Key Constraints & Reminders

1. **Pilot clinic is on-premise OpenDental.** The primary connection is Local API or API Service mode via a local agent. The OpenDental HTTP client MUST support both Local/Service mode (no throttling, 1K pagination) and Remote mode (throttled, 100 pagination) based on clinic config. Build the client to adapt automatically.

2. **Local agent is required for on-premise clinics.** DentalFlow cloud (Azure) cannot directly reach an on-premise OpenDental server. A lightweight agent must run at the clinic, maintaining an outbound WebSocket to Azure. This is the same "agent" shown in the prototype's Agents screen — it's now a real component.

3. **Pilot payers are commercial, not Medicaid.** Delta Dental, MetLife, and Cigna require full benefits parsing (deductibles, maximums, coverage percentages, copays, waiting periods) — not just active/inactive. The eligibility result model MUST support the full commercial benefits fields.

4. **Clearinghouse 270/271 is the primary eligibility path.** A single clearinghouse integration covers all three pilot payers plus hundreds more. Evaluate DentalXChange, Availity, pVerify, and the open GitHub API Ilyas found. Per-transaction cost is typically $0.20-$0.50.

5. **EOBs from commercial payers should come via EDI 835.** Delta Dental, MetLife, and Cigna all support electronic remittance advice (835) through clearinghouses. This gives structured data instead of portal scraping. The EOB parser should handle 835 format as the primary input.

6. **Pagination at 1,000 items in Local/Service mode.** Any data pull that could exceed 1,000 records must loop with Offset. In Remote mode (sandbox), the limit is 100.

7. **Dual-key auth on every request.** Both developer key AND customer key must be in the Authorization header. Format: `ODFHIR {DeveloperKey}/{CustomerKey}`

8. **PHI never in logs or error messages.** The errorHandler middleware must scrub patient names, DOBs, insurance IDs, etc. before any error is logged or returned to the client.

9. **The front-end design system is non-negotiable.** Dark glassmorphic theme, cyan accent (#22d3ee), DM Sans + Space Mono, no Tailwind, styled-jsx only. Do not introduce new CSS frameworks.

10. **Mock data structure mirrors production.** The mock JSON files in `data/mock/` were designed to match this schema. Use them as reference for expected data shapes.

11. **OpenDental's InsVerifies PUT is the key write endpoint for eligibility.** It updates the verification status and date that appears in the insurance verification module within OpenDental.

12. **EOB posting uses ClaimPayments POST + ClaimProcs POST.** This is a $30/month Standard tier operation. Each insurance payment needs a ClaimPayment record and associated ClaimProc line items.

13. **The PMS adapter pattern is the foundation of future expansion.** Every feature must go through IPMSAdapter — NEVER call OpenDental endpoints directly from business logic.

14. **Fallback search logic is critical.** When verifying eligibility, if subscriber ID fails, try name + DOB. This is a real-world requirement — patients often have incorrect or outdated IDs in the system.

15. **Hosting is Azure.** NiftyByte has existing Microsoft licensing. Use Azure Database for PostgreSQL, Azure App Service (or Azure Container Apps), Azure Key Vault for credential encryption, Azure Monitor for audit logging. HIPAA BAA is already included in the Microsoft Product Terms.
